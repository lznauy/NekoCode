# 工作模式教学

**主要读者：** 日常使用 NekoCode 的用户。本文说明如何选择模式、完成任务，以及处理模式切换时的常见问题。实现细节见第二部分：[工作模式框架原理](../developers/INTERACTION_MODES.md)。

## 1. 三种模式怎么选

工作模式决定这轮任务怎样完成。权限设置决定执行时如何审批；两者可以分别选择。

| 模式 | 适合的任务 | 谁执行读取、检索、命令和修改 | 主要限制 |
| --- | --- | --- | --- |
| Standard | 日常问答、排查、开发和修复 | 主 Agent 可直接执行，也可委派子任务 | 遵守当前权限、工作区、沙箱和工具自身规则 |
| Plan | 先了解现状、讨论设计、形成实施方案 | 主 Agent 使用获准的只读工具 | 禁止 shell、修改和子任务委派 |
| Super Agent | 希望主对话专注拆分与验收，由子任务完成执行 | 子 Agent 执行，主 Agent 编排与汇总 | 主 Agent 不能直接读取文件、检索网页、运行命令或修改文件 |

Standard 也支持子任务。Super Agent 的区别在于强制把执行交给子任务，即使只是读取一个文件或运行一次测试。

模式不会自动更换模型。主对话继续使用当前模型；子任务可以通过 Agent Profile 指定其他模型，不指定时跟随主模型。

## 2. 选择与切换

在 NekoCode 输入框中输入，以下不是终端命令：

```text
/mode
```

这会打开模式菜单。也可以直接切换：

```text
/mode standard
/mode plan
/mode super-agent
```

TUI 输入框底部的 `Mode` 在 `Follow` 前，该标签仅显示当前模式；按 `Ctrl+O` 或输入 `/mode` 打开选择器；方向键或 Tab 选择，Enter 确认，Esc 关闭。GUI 也提供模式选择器。切换不会清除输入草稿和图片。

当前协调轮次执行、等待审批或等待回答时，不能切换模式。后台任务或排队输入存在时，可在前台空闲后切换会话、模式、模型及推理深度。旧任务保持原会话、执行模型和工具快照；旧会话的排队需求与自动验收等待切回该会话的 Super Agent 模式再处理。刷新扩展、替换 MCP、修改完整配置及删除会话仍受资源使用屏障保护。Super Agent 的普通新输入作为独立需求处理，不再默认追加到旧子任务。

模式按会话记忆：

- 新会话默认 Standard；恢复会话会恢复其模式，分叉会话继承来源模式。
- 空白会话中的选择会留在当前草稿内，但空白草稿不会因此出现在已保存会话列表中。
- 结束或取消一轮任务不会重置会话选择。
- 恢复了当前版本不认识的模式时，可以查看历史，但需要先用 `/mode standard` 等命令选择受支持模式，才能继续执行。

`Follow` 只控制滚动跟随，`Perm` 控制审批；修改它们不会切换工作模式。FULL 也不能解除 Plan 或 Super Agent 的工具限制。后台执行期间，同一会话中已派发的子任务会实时跟随当前手动、AUTO、FULL 审批模式。审批状态按父会话隔离，切换其他会话不会改变原任务的模式；切回时恢复原会话的审批选择。FULL 不绕过显式 deny 规则，也不扩大工具范围；AUTO 仍对危险或无法判定的调用请求审批。

## 3. Standard：直接完成任务

```text
/mode standard
```

再输入需求，例如：

```text
检查登录失败的原因，修复后运行相关测试，并说明改动。
```

Agent 可以自己读取文件、搜索、修改和测试，也可以把独立工作交给子任务。是否需要审批，继续由权限规则和沙箱要求决定。

这里的“可以执行”不等于自动获准。工具仍要检查工作区、审批、沙箱和写入条件；例如修改已有文件前可能需要先读取文件。

## 4. Plan：先调查，再形成方案

```text
/mode plan
```

例如输入：

```text
调查当前登录链路，给出增加验证码登录的方案。
说明涉及哪些模块、兼容性风险和验收步骤，先不要实现。
```

Plan 可以通过文件读取、代码搜索、网页检索以及获准的索引和 LSP 工具收集证据，返回方案。它不能通过 shell 运行 `git status`、测试或其他命令，即使某条命令本身不修改文件，也会被拦截。

方案确认后，需要显式切换执行模式：

```text
/mode standard
```

然后再发送“按刚才的方案实现”。如果只回复“可以”而没有切换，持久 Plan 模式仍然有效。也可以改选 Super Agent，让子任务实现和验证。

### 只让一轮进入 Plan

不想改变会话默认模式时，用：

```text
/plan 调查当前登录链路，给出增加验证码登录的实施方案
```

`/plan <任务>` 只影响这一轮，TUI 会以 `Plan*` 标记。结束后，下一轮继续使用原来选择的模式。例如原来是 Super Agent，这一轮规划结束后仍回到 Super Agent。

## 5. Super Agent：主对话编排，子任务执行

```text
/mode super-agent
```

例如输入：

```text
调查网页抓取失败的原因，修复后验证。
先把来源解析和重试链路分开调查；涉及同一文件的修改按顺序进行。
最终说明根因、改动、测试结果和未验证事项。
```

典型过程是：

1. 主 Agent 理解需求、拆分工作，按需查看可用执行者。
2. 通过 `task_submit` 委派调查，立即获得任务 ID 和接收凭据，随后结束本轮回复。
3. 后台任务继续运行；你可以发起另一项需求。任务完成后，Runtime 自动启动新的协调轮次，主 Agent 验收结果并安排后续工作。
4. 修改完成后，再委派验证；最后汇总结果和未解决事项。

主 Agent 可以根据对话中已有信息直接回答问题，不必为了每句话创建子任务。但只要需要读取新文件、检索、运行命令、修改或测试，就必须委派。

### 执行者如何分工

| 内置 Profile | 用途 | 能力边界 |
| --- | --- | --- |
| `explore` | 标准模式中的阅读、检索、调查 | 只读，不提供 shell 和工作区写入工具 |
| `coder` | 标准模式中的实现、修复和运行命令 | 在其工具范围及当前权限内执行，包含 shell、编辑和测试所需工具 |
| `executor` | 通用任务、媒体理解与生成、已配置的外部服务 | 仅 Super Agent 可委派；按派发时捕获的工具范围执行，继续遵守审批和沙箱 |

Super Agent 固定使用专用 `executor`，派发工具不提供 Profile 选择；`explore`、`coder` 和自定义 Profile 保留给标准模式。主 Agent 可以并行派出多个 executor 实例。派发时通过 `required_tools` 声明必需工具，宿主会在启动子任务前检查是否具备。需要 `git status/diff`、测试等命令时，使用默认 `tool_scope="general"` 并声明 `required_tools=["shell"]`；“只审查、不改文件”写在任务约束中。纯文件阅读与检索可以显式选择 `tool_scope="read_tools_only"`，该范围不包含 shell、写入工具或 MCP，可并行执行。旧 `read_only` 参数会被拒绝并提示正确用法，避免启动后才发现工具不足。FULL 和审批只能决定可见工具如何执行，不能补上被工具范围排除的 shell。

自定义 Profile 可以声明更窄的工具范围、技能、步数和可选模型，见 [自定义 Agent 指南](../developers/AGENT_GUIDE.md)。技能只提供工作流，不会扩大执行者的工具范围。内置 Profile 也不等于主对话所有已注册工具的完整副本。

### 查看、继续和取消任务

TUI 使用 `/tasks` 或 `Ctrl+G` 查看当前父会话的子任务、状态、轮次和输出，具体操作见 [查看子任务](USER_GUIDE.md#查看子任务)。关闭任务浮层不会取消任务。排队期间也可进入详情查看本次派发的任务提示词全文，不必等待执行开始；恢复任务的排队视图展示新指示，旧轮次仍可从轮次列表查看。

需要继续已有子任务时，可以让主 Agent 找到原任务并继续；模型通过 `task_list` 查找，再用 `task_submit` 的 `resume_id` 恢复 executor 任务。旧 explore/coder/自定义任务不能通过该入口恢复；可在标准模式继续旧任务，或新建 executor 任务并提供旧结论作为参考。使用的是任务 ID，而不是某一轮尝试的 ID。

Super Agent 中，结束或取消当前主对话轮次不会取消已受理的后台任务。可以明确要求主 Agent 用 `task_cancel` 取消指定任务；Runtime 也提供按任务 ID 取消的接口。取消不是撤销：已完成的文件修改不会自动回滚。Standard 的同步子任务仍随主运行取消。

### 子任务如何交接结果

完成通知会在总计 64 KiB 的报告正文预算内直接交付结果，并通过 `result_complete` 标明每份报告是否完整。通知还包含同批任务清单 `group_tasks` 和进行中的任务数 `pending_tasks`，便于主 Agent 区分阶段进度与最终汇总。`task_list` 中的结果仍是预览。

报告不完整时，主 Agent 用通知中的 `read_result` 参数调用 `task_result`，再按返回的 `next_call` 分页读完；工具会保留精确的结果引用，无需反复复制长 `result_ref`。读取失败必须补读或明确报告证据缺口。汇总时逐项核对各子任务的发现、来源、验证状态和处理结论，合并重复项并说明排除原因。这个工具只读取当前父会话的子任务结果，不提供项目文件或命令权限，也不需要另派一个子任务翻会话文件。

首次传入任务 ID，可用 `attempt_id` 指定执行轮次；返回 `result_ref`、`next_offset` 和 `has_more`，有后续页时同时返回 `next_call`。后续页优先直接使用 `next_call`，也可显式使用同一个 `result_ref`，直到 `has_more=false`。引用固定具体轮次和内容版本，A 后来继续执行也不会让旧引用变成新报告；它不证明报告正确。

B 需要使用 A 的结果时，主 Agent 在派发 B 时传入 `inputs: [A 的 result_ref]`。B 会获得有界预览，并可通过自己的 `task_result` 读取被明确分享的引用。没有 inputs 的执行者不会获得该结果工具；该工具不允许 B 任意查询其他任务。文件读取仍遵守原有文件权限与沙箱，结果引用不授予额外文件访问权。

只有已保存终态结果才能作为 inputs，部分完成、失败和中断仍保留其真实状态。恢复 B 时省略 inputs 会沿用已保存范围，显式提供只能收窄；需要新的输入结果应新建任务。需要提前排流水线时，在新任务中使用 `after: [上游任务 ID]`；最多 8 项，且与 inputs 合计不超过 8 项。只接受当前父会话已经受理的任务，不接受自己、重复项或未来任务 ID。等待依赖不占执行槽位；全部上游成功完成后，下游自动获得对应终态结果并开始。上游失败、部分完成或取消时，下游显示“上游未成功”，不会执行。恢复旧任务不能添加新的 after，应新建任务。

### 直接管理后台任务

- `/background`：查看任务 ID、状态、验收投递、用量和未接收的追加数量。
- `/task-review <任务 ID>`：显式重试失败的结果验收，不会重新执行子任务。
- `/task-find <任务 ID> [--after=序号] <关键词>`：搜索已保存的工具输出，按返回的序号继续翻页。
- `/task-export <任务 ID> <新文件路径>`：流式导出该任务各轮工具输出，拒绝覆盖已有文件。
- `/task-add <任务 ID> <内容>`：向指定任务追加指示，不经过主 Agent 转发。
- `/task-stop <任务 ID>`：请求停止指定任务，其他任务继续运行。
- `/tasks-stop`：停止当前会话的协调轮次、后台任务和排队需求，并提示停止任务数及不再自动验收的未消费结果数；结果记录仍保留。
- `/inbox`：查看排队需求及恢复状态。
- `/demand-resume <需求 ID>`：继续重启前尚未开始的需求。
- `/demand-discard <需求 ID>`：忽略待处理或中断的需求记录。

GUI 在 Super Agent 模式下于输入框上方显示后台任务汇总，展开可查看任务状态、向指定任务追加指示、停止单个任务或停止全部。面板中的“新需求”在协调者忙碌时也可提交，受理后排队，实际开始处理时才加入对话。面板中的需求收件箱可继续尚未开始的恢复需求，或忽略待处理、中断记录。审批和提问按请求顺序展示，并标明所属子任务，其他任务的请求不会覆盖当前请求。

追加成功表示已排队。子任务在下一轮模型请求前接收，不会打断正在执行的工具。最后一轮期间收到的追加可能来不及处理，会保留为未读，显式恢复原任务时继续接收。追加以任务内递增序号去重：保存成功但尚未确认消费时退出，恢复后不会再次加入同一条已保存指示。“停止全部”会抑制这批任务后续的自动验收，避免又派发新任务；之后仍可提出新的需求。它不会回滚已发生的修改。

### 当前运行边界

后台子任务跨协调轮次共用 8 个执行槽位，超过上限排队。主对话每次只处理一轮模型请求，任务在后台并行。协调者正在处理时，新的纯文本需求进入有界队列；图片和控制命令需等待短协调轮次结束再发送。GUI 的普通对话输入在协调者回复期间保留发送锁，可通过后台面板的“新需求”提交纯文本独立需求。

任务记录和完成通知保存在父会话的 `background.json`；执行结果保存后才通知主 Agent。程序重启后，未结束任务标记为中断，不会自动重做修改；已开始但未确认成功的验收轮次也不会自动重放，需要显式继续。排队的新需求在回执前保存到同一文件。重启后，未开始的需求显示为“待处理”，需在 GUI 收件箱或 `/demand-resume` 中明确继续；已经开始的需求显示为“中断”，需先检查对话和实际修改，再发起新需求，不能直接重放。需求回执记录的是协调轮次的处理状态，后台执行仍以任务状态为准。子 Agent 不能继续创建下一层子 Agent。

Super Agent 后台执行只使用专用 `executor` 的独立工具箱。`executor` 可使用可信注册的文件、命令、网页、已配置媒体工具和具体 MCP 目标；不会继承所有父对话工具，也不默认获得 FULL。未提供独立绑定的扩展工具会在提交前明确拒绝。

MCP 只绑定提交时已就绪的工具及其原连接；服务执行中被替换或关闭时，旧任务的绑定失效，不会转向新服务。已有 `executor` 恢复时，工具范围只能保持或收窄，不会自动获得后来添加的能力。需要新能力应新建任务。

worktree 内的 `executor` 不提供 MCP，因为已配置服务可能仍以原工作目录运行。可把 MCP 工作拆成共享工作区的独立任务。

多个任务默认可能共享工作区。系统保守串行调度同一共享工作区的写任务；只读任务可并行。普通 Standard 前台执行也受写入互斥约束，后台写任务仍在运行时需等待，或使用 Plan/Super Agent；Standard 前台执行期间，后台写任务等待其完成。独立修改可使用 worktree 隔离，隔离任务不占同一共享写锁。

## 6. 常见问题

**为什么 FULL 下仍提示模式禁止？**

FULL 影响审批，不会扩大模式允许的工具。Plan 的 shell 和写入、Super Agent 主对话的直接执行仍被禁止。

**为什么 Super Agent 的子任务能写文件，主对话却不能？**

两者承担不同角色。主对话只编排；执行者按自身 Profile 工作，仍受继承的权限规则、工作区和沙箱限制。

**为什么子任务显示完成，主对话还会继续安排任务？**

一项调查完成不代表整个需求完成。主 Agent 需要验收证据，并可能继续委派修改或验证；部分完成、失败和未验证项应在最终答复中说明。

**可以只靠自定义 Skill 增加一种工作模式吗？**

不能。Skill 是工作流说明；工作模式还包含运行快照、策略绑定和工具硬限制。当前新增模式需要修改框架代码，原理和接入位置见 [第二部分](../developers/INTERACTION_MODES.md#7-如何扩展模式)。

### 后台汇总、任务档案与失败验收

TUI 在主对话空闲时也显示后台进行中数量、未读追加、待重试验收和累计 token。`/tasks` 浮层按 `a` 切换当前会话/全部会话，跨会话行标明父会话；按 `d` 确认删除任务。任务归属使用父会话和任务 ID 的组合，其他会话的同名任务不会混在一起。查看其他会话历史不会自动续跑。

GUI 在各模式下提供“任务档案”，可切换全部会话、分页查看轮次和过程、按已提交序号读取完整工具输出、搜索、导出和确认删除。后台面板收到状态事件后刷新，并保留每 5 秒完整重同步。跨会话导航会丢弃旧页面的迟到响应。

验收失败保留任务结果、投递次数和错误。GUI 的“重试验收”和 `/task-review` 只重新排队协调者验收；操作者应先检查原对话与实际修改。已经停止整批任务的通知不会被此入口恢复。切走会话后，重试请求等待回到所属会话的 Super Agent 模式。

删除仅清理任务记录、专属工具输出与观测缓存，保留主对话已有引用、文件修改和 worktree。活动任务、等待依赖的任务、正在验收或被下游使用的任务不能删除。删除与续跑共享存储锁；清理失败可对相同 ID 重试。删除标记阻止旧运行事件重新显示该任务。累计已消耗用量不会因删除任务而减小。

后台用量按原父会话累计，包含已淘汰/删除任务的开销，与当前前台轮次分开。用量检查点保存到 `background.json`，恢复时与子任务规范记录对账。实际执行的后台事件按本次执行的独立 ID 归档到原父会话，前台切换不会改变归属。重启仍不自动重放未完成操作。


多步骤任务可以使用通用待办清单，Standard、Plan 和 Super 共用同一套保存与收尾规则，不要求每项派出子任务。清单会区分待处理、进行中、完成、受阻和取消；完成项记录简短结果，受阻或取消保留原因。切换模式或重启不会删除已保存计划；继续旧需求时，Agent 可用返回的 plan_id 恢复原清单，新需求不会自动接管旧任务。已有后台任务时可先给进度说明；没有运行任务且仍有可推进项时，Agent 会继续核对清单，而不是只总结前几项就结束。
