# 自定义 Skill 指南

> **主要读者：** 用户侧扩展作者。编写、调用和分享自己的工作流。

Skill 是按需加载的工作流程。它告诉模型在某类任务中按什么步骤处理、需要哪些证据以及如何交付，不会单独创建一个执行者或增加工具权限。

本文创建 `change-review`，用于根据明确范围阅读代码并报告问题。需要独立子任务时，配合 [自定义 Agent](AGENT_GUIDE.md)；需要分发时，打包成 [Plugin](PLUGIN_GUIDE.md)。

## 一、创建一个项目技能

在项目中创建以下文件：

```text
.nekocode/
└── skills/
    └── change-review/
        └── SKILL.md
```

`SKILL.md`：

```markdown
---
name: change-review
description: 用户要求审查指定代码或改动、检查正确性及维护性时使用；不用于一般功能开发。
---
先确认用户指定的文件、差异或审查问题。范围不足时，指出缺少的信息。

1. 阅读目标代码及直接相关的调用方，不凭文件名猜测行为。
2. 优先检查可复现的正确性问题，再检查会增加后续修改成本的重复逻辑。
3. 每项发现给出文件位置、触发条件、影响和依据；不把猜测写成确定问题。
4. 只执行当前工具和授权范围内的验证。无法验证时明确说明原因。
5. 除非用户要求修复，只报告问题，不修改代码。

交付：按严重程度列出发现，并说明已执行的验证；没有发现时如实报告。
```

frontmatter 用两行 `---` 包住，后面是正文。`name` 和 `description` 必填，名称建议与目录一致，使用简短的字母、数字和连字符。

名称是调用标识；描述要写清“何时使用”和“不用于什么”，不要只写“专业代码专家”。流程、输出要求和详细材料放正文，避免把长篇指令堆进描述。

## 二、加载和调用

项目技能放在 `<项目>/.nekocode/skills/`；希望所有项目都能使用时，放在 `~/.nekocode/skills/`。每个技能是一个含 `SKILL.md` 的目录。

创建后在 NekoCode 输入框执行：

```text
/workspace reload
```

再明确调用技能：

```text
$change-review 审查 bot/policy/contract/result.go 的结果合并逻辑，只报告问题。
```

这些是 NekoCode 输入，不是终端 Shell 命令。也可以直接说明审查需求，让模型根据技能描述选择。自然语言自动选择并非确定性触发器；希望每次指定步骤时，用 `$技能名` 明确调用。

运行时先提供技能名称和描述，完整正文按需加载。模型可通过 `skill` 工具按名称加载内容；Skill 本身不会自动执行目录里的脚本。

修改后刷新发现目录。已进入当前对话的旧正文不会因此从历史消息中消失，验证新版本建议使用新会话或确认本次已加载新内容。

## 三、同名技能与覆盖顺序

同名技能按以下顺序选择，第一份完整定义生效：

```text
项目技能 → 用户技能 → 已激活插件技能 → 内置技能
```

同名定义不会合并。比如项目中有 `change-review`，插件里也有同名技能，本项目使用项目版本。插件 Agent 的 `skills: [change-review]` 同样按当前宿主的技能目录解析，不保证总是使用插件自带文件。

重用内置名称可能覆盖原有流程。给团队技能取有辨识度的名称，并在跨项目分享前检查名称冲突。

## 四、拆分辅助材料

当正文过长，可以把细节放到独立文件：

```text
change-review/
├── SKILL.md
├── references/
│   └── checklist.md
└── templates/
    └── report.md
```

例如，在正文增加：“审查前读取本技能 `references/checklist.md`，仅在需要交付报告时读取 `templates/report.md`。”这些文件需要实际创建，不会由目录示意自动生成。

加载后的技能内容会提供技能目录和辅助文件的绝对路径。读取材料时使用这些路径；输出写到当前工作目录，不要写回技能安装目录。辅助文件只提供索引，不会全部自动注入模型上下文。

正文应能单独说明任务步骤，不要依赖一个未被读取的长附件才能判断下一步。完整格式化内容超出工具输出预算时，加载会报错而不是截断说明；可把案例和详细参考移到辅助文件，减少正文与文件列表长度。

## 五、哪些字段现在真正有作用

新技能先使用 `name`、`description` 和 Markdown 正文即可。

`context` 可省略或设置为 `inline`。`disable-model-invocation: true` 表示仅限用户手动选择：仍可通过 `$技能名` 或技能选择入口加载，但不会出现在模型技能目录和 `skill` 工具枚举中；模型直接调用、`task.skills` 和 Profile 的 `skills` 预加载都会被拒绝。省略或设为 `false` 保持普通技能行为。它约束加载入口，不是文件保密或工具权限边界。

`context: fork`、其他 context 值，以及 `allowed-tools`、`agent`、`max_steps`、`context_window` 暂不支持。只要出现这些执行字段（即使值为空或零），该文件就会加载失败，避免配置看似有效却未执行。其他描述性元数据仍可保留。

输入 `/skills` 查看已加载的技能、手动专用标记，以及无效技能的完整文件路径和错误原因。修正后重新加载扩展或重启会话以更新结果。

需要独立子 Agent 时，通过 `task` 选择 Profile；需要工具范围和执行步数上限时，在 Agent 文件中配置 `tools`、`max_steps`。需要确定性的事件检查时使用 [Hook](HOOK_GUIDE.md)。

普通技能也不会因正文写了“允许写文件”而扩大权限。用户请求、执行者工具上限、审批和沙箱仍然适用。

## 六、配合自定义 Agent

安装并启用 `review-agents/reviewer` 后，可以让主 Agent 委托它，同时附带技能。对应的 `task` 参数示意为：

```json
{
  "profile": "review-agents/reviewer",
  "skills": ["change-review"],
  "prompt": "只读审查 bot/policy/contract/result.go，报告具体位置和依据。"
}
```

这段 JSON 是模型工具参数，不是斜杠命令。默认技能也可写进 Agent 的 `skills` 数组，详见 [Agent 指南](AGENT_GUIDE.md)。

技能要求的验证必须与执行者能力相符。示例审查员没有 Shell，不能因为技能提到测试就宣称运行了测试。

## 七、排查与分享

| 现象 | 优先检查 |
| --- | --- |
| 提示技能不存在 | 是否从正确项目启动、文件名是否为 `SKILL.md`、是否刷新 |
| 有文件却没有被发现 | YAML 是否合法，`name`、`description` 是否缺失；解析失败的技能会被跳过 |
| 执行的是另一份流程 | 查看同名技能覆盖顺序和当前加载的绝对路径 |
| 没有自动使用 | 描述是否明确；先用 `$change-review` 确认显式调用 |
| 修改后仍看到旧内容 | 是否修改了实际生效文件；新会话是否仍有相同现象 |
| 声明工具字段却没限制工具 | Skill 元数据不是当前工具权限边界，改用 Agent 配置 |

验证时选一段范围明确的代码，检查模型是否遵循交付要求并如实说明验证情况。文件能加载只说明格式和发现链路可用，不证明模型一定遵循每一步。

个人使用可直接复制技能目录；团队分发可把同一个目录放进插件的 `skills/`，通过 manifest 声明，见 [Plugin 指南](PLUGIN_GUIDE.md)。技能源码及解析实现见 [Skill 加载器](../../bot/extension/skill/load.go)。
