# Subagent 后续优化方案与风险评估

状态：精简版 MVP 已实现：持久 attempts、崩溃恢复、当前父会话 `task_list`、attempt-aware Runtime，以及执行中状态区、完成后结果优先的 TUI。正文 token 流式、全局管理、删除和多端完整接入仍是后续设计草案，不授权数据迁移或删除。

现有实现和操作说明分别见 [数据目录设计](DATA_DIRECTORY.md#subagents--子任务会话)、[用户指南](USER_GUIDE.md#查看子任务) 和 [Runtime 应用指南](RUNTIME_APP_GUIDE.md)。这些文档描述现状，本文描述后续演进。

## 1. 目标与边界

一个 subagent 对应一项可持续的任务；一次 `task` 调用对应一次执行。主 agent 决定新建还是续跑，用户能查看执行过程、历史结果和保存的任务。

继续保持以下交互原则：

- 主窗口承载主 agent 的执行和用户交互，子任务通过 `Ctrl+G` 浮层查看。
- 主窗口显示简短任务摘要和需要处理的失败，不展开所有子任务输出。
- 详情复用主 agent 的消息与工具渲染组件，按需读取历史和完整输出。
- 任务结束后默认突出结果，过程仍可查；正在阅读时不因任务结束而跳页或折叠。
- 续跑加载保存的上下文，开始新的执行，不维持永久存活的进程。

本轮方案不包含独立作业服务、跨进程自动恢复等待队列、跨父会话直接续跑、工具副作用的 exactly-once 保证。工作区隔离、单任务取消属于独立设计范围，不能通过增加观测界面顺带承诺。

## 2. 当前实现基线

| 能力 | 当前情况 |
| --- | --- |
| 调度 | `max_concurrent_subagents` 默认 8；超出后在进程内排队，不占普通工具执行名额 |
| 持久化 | 每个任务保存快照、完整 transcript、索引和观测摘要，归属于父会话 |
| 续跑 | `task` 的 `resume_id` 可继续当前父会话中的任务，保留原 profile，省略 skills 时沿用原技能 |
| 恢复安全 | 获得执行锁后恢复；未确认完成的工具结果标为未知，不自动重放；指令和权限按当前配置重建 |
| 轮次 | 每次正式执行保存独立 attempt 身份、递增序号、输入、结果、用量和 transcript 范围；旧记录不反推历史轮次 |
| TUI | 执行中显示紧凑状态，完成后默认当轮结果；`p` 展开过程、`[` / `]` 切换轮次，支持历史分页、工具详情和大输出分页 |
| 实时展示 | 工具状态与预览实时更新；模型正文在完整消息保存后出现，尚非完整正文流式体验 |
| 全局管理 | TUI 默认只列当前父会话任务；尚无全局持久化任务管理和独立删除入口 |
| 客户端 | Runtime 提供任务查询能力；GUI、HTTP 等尚未具备与 TUI 等价的完整任务浏览能力 |

现有目录保持不变：

```text
~/.nekocode/sessions/<parent-session-id>/
├── subagents/<subagent-id>/
│   ├── session.json
│   ├── messages.0.json / messages.1.json
│   ├── transcript.jsonl
│   ├── transcript.idx
│   ├── observation.json
│   └── .active.lock
├── tool-results/subagents/<subagent-id>/
└── runs/<parent-run-id>/events.jsonl
```

父 Run 的事件保留策略和子任务正文的生命周期不同。任务历史不应依赖父 Run 事件文件始终存在。排队但尚未开始的任务也不能被误认为已有可恢复上下文。

## 3. 新派与续跑规则

判断依据是是否继续同一项工作，而不是提示词是否相似，或进程是否还活着。

| 场景 | 决策 | 注意事项 |
| --- | --- | --- |
| 补充要求、验证修复、继续未完成工作 | 续跑 | 检查旧结果和当前工作区状态 |
| 临时网络错误、取消后继续 | 续跑 | 上次工具结果未知时先检查现状 |
| 新目标、新职责、需要不同 profile | 新派 | 提供明确目标、约束和必要背景 |
| 独立复核原结论 | 新派 | 避免原上下文影响判断，结论仍须验证 |
| 原上下文严重偏离目标或积累过多无效尝试 | 新派 | 传递必要的证据和交接摘要，不整段复制旧上下文 |

保留 `task(profile, skills, prompt, title?, resume_id?)`：省略 ID 新建，提供 ID 续跑。底层不根据文本相似度自动复用，也不把失败请求自动转换为新任务。

已提供只读 `task_list`，默认查询当前父会话，返回分页、有界摘要、完整任务 ID、profile、状态和最近 attempt。主 agent 借此查找可续跑任务，不依赖记忆或扫描目录。全局管理可见性不等于跨父会话执行权限。

## 4. 数据与事件约束

### 4.1 任务与执行轮次

保留稳定 `subagent_id`，每次正式执行分配独立 `attempt_id`。当前执行轮次记录输入、状态、开始和结束时间、本次用量、结果及 transcript 范围；任务投影区分 queued、running、等待交互与终态，queued 占位没有 attempt，不能把“未开始”当作“执行失败”。

界面可显示一个任务下的多次执行，历史结果不被新结果覆盖。父 Run 关联及任务级累计用量尚未进入当前 attempt DTO，属于后续增强，不计入阶段 1–3 已完成范围；新增时应与本轮用量分开，避免续跑重复计数。

当前 attempt 与任务元数据一起保存在 `session.json`，活动正文使用双槽消息文件，完整消息仍追加到 transcript。后续若调整轮次物理格式，必须先评审提交顺序与崩溃恢复设计，不额外创建第二套权威日志。

### 4.2 恢复依据与投影

- 已提交的 transcript 前缀与对应快照组成上下文恢复依据，未提交尾部不参与只读展示。
- 任务和轮次状态必须有明确的权威来源；Runtime 快照、观测缓存和全局目录索引不得成为相互覆盖的独立真相。
- 实时事件用于即时展示，允许中断或重复；重连必须能用持久记录纠正界面。
- 所有重建缓存均可删除、重建，不能因缓存损坏丢失任务。
- 保留工具副作用前保存调用、执行后保存结果两处 checkpoint；不可因看似重复而合并。
- profile 的恢复前预检与开始执行时的约束承担不同职责：拒绝错误请求前不能先修改历史。

### 4.3 流式消息身份

正文流式显示前，生产端必须提供稳定的执行轮次、消息身份和增量顺序。任务 ID 不能单独承担消息去重；不使用文本相等或前缀比较推断增量归属。

完整消息保存后，应替换对应临时流式消息，避免重复追加。订阅与读取历史之间的竞态、事件重发、迟到消息和续跑切换都要有测试。连接丢失时显示同步状态；历史查询失败时保持已有内容和阅读位置。

不要求每个 token 单独写入 transcript。实时刷新、完整消息提交与事件录制可以采用不同粒度，但其职责、恢复边界和体积预算必须明确。

## 5. TUI 展示与管理

### 5.1 列表

默认当前父会话，保留搜索，增加失败、等待处理等简单状态筛选和最后活动时间。异常状态要容易找到，后台刷新不抢走选中项。

“全部已保存任务”作为管理范围，按父会话分组，分页查询，不一次加载所有上下文。选择其他父会话的任务可以只读查看；继续执行时进入所属父会话并重新校验工作目录和权限。

### 5.2 详情

| 状态 | 默认展示 | 过程入口 |
| --- | --- | --- |
| 执行中 | 目标、状态、当前执行的实时过程 | 历史轮次默认折叠 |
| 已结束且首次打开 | 最终结果、验证情况、未完成事项、失败原因 | 可展开本次及历史执行 |
| 浏览过程中执行结束 | 保持当前阅读位置，提示结果已就绪 | 用户主动进入结果 |

`Esc` 逐级返回，`Ctrl+G` 收起浮层，收起不取消任务。审批和提问优先获得交互焦点，处理后恢复观察。窄窗口和小窗口继续适配，不引入长期并排的多窗口布局。

### 5.3 工具调用与完整输出

所有已保存的工具调用都能查看，默认展示名称、状态和短预览。工具详情按需展示完整参数和结果，大输出分页读取，增加搜索与导出。

“完整可查”指全部已保存内容有访问路径，不代表一次渲染全部字节，也不承诺工具本身未丢弃的数据可以恢复。明确区分预览被缩短、原始输出不完整、文件已缺失和记录已删除。

### 5.4 手动删除

计划在列表提供 `d` 删除和确认，列明任务记录、专属输出和不可恢复性。排队、执行中或等待用户处理的任务禁止直接删除。

删除必须在存储层与新执行互斥，不能只依赖 UI 的状态检查。需处理任务目录与工具输出目录部分清理失败、跨进程竞争、缓存失效及父会话删除；失败可诊断和重试，不能误删其他任务。

父对话和父 Run 里已有的引用、摘要或输出不随子任务删除而改写；访问已删除记录时明确提示。删除子任务不是清除所有历史副本或备份。删除事务与锁顺序必须在实现前单独评审。

## 6. 各端可观测性兼容

```text
task 工具 → Bot / 子任务引擎 → 会话存储
                    ↓               ↓
                 Runtime ← standard 适配
                    ↓
          TUI / GUI / HTTP / headless / IM
```

上层只依赖 Runtime，不能让各客户端自行解析目录、拼接快照或合成不同的任务状态。

| 层面 | 后续要求 |
| --- | --- |
| Runtime | 统一任务、轮次、历史、输出查询和能力声明，明确订阅、重放与断流语义 |
| TUI | 按能力启用新详情；缺少服务时保留原有展示或明确降级 |
| GUI | 接入相同 DTO 和轮次语义，不能仅有启动、结束事件就声称完整支持 |
| HTTP | 增加对应只读分页接口，正文和原始输出与现有隐私安全摘要接口分开 |
| headless / ACP | 逐项验证新增字段、未知事件、工具身份关联和可靠订阅行为；不宣称自动获得与 TUI 相同的能力 |
| IM | 保持结果和审批优先的推送策略，不把每条子任务进度发送到聊天中 |

新增字段优先兼容缺省值；旧格式 `evt_N` 缺少 Sequence 时，在游标过滤前规范化。旧事件和导出接口不因仓库内无调用而直接删除，是否弃用需评估外部下游。

## 7. 实施顺序与验收

此前的七项功能按依赖调整为以下阶段，避免同时修改存储、流式协议和删除机制。

| 阶段 | 范围 | 验收门槛 |
| --- | --- | --- |
| 1：数据与轮次基础 | 定义状态来源、执行轮次、历史边界、旧数据兼容和提交顺序；实现最小轮次记录 | 三次续跑是一个任务、三次执行；崩溃恢复不串轮次、不重复计量；工具调用与结果的保存边界可验证 |
| 2：工具规则与观测契约 | 完善新派/续跑说明，实现只读任务查询；确定消息身份、游标和客户端能力声明 | 能查到旧任务并继续；运行中重复调用、错误 profile 和跨父会话续跑被拒绝；旧客户端可降级 |
| 3：详情布局 | 结果优先、执行过程可展开、历史轮次折叠，复用现有组件 | 首次查看先看到结论；正在阅读时不跳页；续跑不覆盖旧结果；窄窗口适配 |
| 4：流式与完整记录 | 实时正文、保存消息合并、断流补齐、工具输出搜索与导出 | 不重复或串接消息；断流可恢复；全部已保存调用可查，大输出读取和渲染有界 |
| 5：全局管理与删除 | 跨父会话只读列表、可重建索引、互斥删除与失败恢复 | 大量任务不全量加载正文；损坏条目隔离；续跑与删除竞争安全；部分清理失败可重试 |
| 6：多端接入与规模验证 | HTTP/GUI 等按能力接入，异常筛选与活动时间，跨端契约测试 | 各端状态一致或明确不支持；百任务并发、千任务分页和长历史保持有界；不依赖全量永久事件缓存 |

阶段 1–3 已实现并通过当前回归测试，是最小可用基线；阶段 4–6 仍是后续设计。已实现范围内若重构存储或事件身份，仍须先评审兼容与故障恢复，不能把已有验收当作后续设计的替代品。

预计涉及 `bot/session`、`bot/agent/subagent`、task 工具与 taskbridge、`bot/core`、protocol、Runtime/standard、TUI 及各传输适配，整体超过 8 个文件。沿用现有服务边界，不增加外部服务、账号、密钥或第三方数据库。

## 8. 风险与必须验证的故障场景

| 风险 | 影响 | 验证与约束 |
| --- | --- | --- |
| 多份状态不一致 | 列表已结束但详情仍运行，或错误恢复轮次 | 在开始、提交、结束各边界注入退出和写失败；投影从权威数据重建 |
| 流式重复、乱序、迟到 | 重复文字、旧执行污染新执行 | 用稳定身份合并；模拟事件重复、消息保存与订阅竞争、重连和续跑切换 |
| 共享工作区并发写 | 文件覆盖、读到中间状态、验证结果失效 | 明确上下文隔离不等于文件隔离；测试两个 coder 修改同一文件；worktree 方案独立评审 |
| 未知工具结果与重试 | 已发生的副作用再次执行 | 执行后保存前中断；恢复先检查现状，不自动重放，也不自动新派 |
| 删除与执行竞争 | 删掉正在使用的上下文或输出 | 同任务续跑/删除、跨进程访问、删除父会话、清理一半失败等测试 |
| 全局扫描与存储膨胀 | 查询越来越慢，内存和磁盘持续增长 | 大列表分页、缓存可重建、按需读正文；量测正文/事件/输出重复保存成本 |
| 完整记录含敏感内容 | 扩大 HTTP、导出和全局管理的暴露面 | 保持现有权限边界，区分摘要与正文接口；评估脱敏与保存职责，不能承诺所有输出安全 |
| 格式或接口升级 | 旧数据不可读，旧客户端失效 | 新读旧数据、旧客户端缺少字段、未知事件和能力缺失测试；写入新格式前说明降级限制 |
| 刷新打断阅读 | 完成、分页、后台同步改变选中项和位置 | 覆盖上下跨页、鼠标滚轮、搜索、暂停重试、工具详情、审批焦点及窗口缩放 |

性能验收先记录当前基线，再比较列表查询、详情打开、滚动、流式刷新、内存和磁盘增长。并发测试使用可控假模型，不以大量真实模型请求替代压力验证。

## 9. 旧数据、回退与决策门槛

- 不强制搬迁现有 transcript 和输出目录，也不根据文字猜测过去的执行轮次。旧记录显示为“旧版记录”，只有已知信息被标注；首次续跑开始记录明确的新轮次。
- 当前实现保留旧记录读取兼容，新格式写入后不承诺旧二进制可读。后续格式升级仍必须明确版本检查、备份与降级行为，不能把代码回滚当作数据回滚。
- 当前轮次元数据、提交顺序与恢复边界见第 2、4 节；后续重构物理格式时，必须重新覆盖部分写入和恢复后再写入的故障场景。
- 消息标识与重连算法：由 Runtime/引擎协议阶段确定并测试后，TUI 才接正文流式。
- 删除事务与锁顺序：由全局管理阶段评审后实施，覆盖执行锁、父会话删除和两个目录清理。
- 全局索引位置及保留策略：在测量扫描成本和重复存储成本后确定；索引必须可重建，自动清理不是本草案已批准的操作。
- 并发写工作区策略：由调度/权限设计单独评估；观测能力不能替代写入隔离。

已完成阶段的既有约束应继续保留；其余条目是后续阶段的实施前决策门槛。每个新阶段完成设计、回归和故障验证后再推进。
